# Agent
에이전트 그래프를 만들거나 바꾸거나 검증·배포 오류를 고치거나 배포 뒤 채팅과 승인을 안내할 때 읽는다. 정의와 배포가 한 리소스다. 정의는 제안이라 사람이 카드에서 고를 때만 draft 로 저장되고, deploy_agent 를 불러야 클러스터에 뜬다.

## 그래프
- Agent 는 graph{nodes[], edges[]} 와 service{budget{session_tokens, daily_tokens}, observability{record_bodies}, evaluation} 로 이뤄진다. service 는 템플릿 값을 그대로 써도 되고 evaluation 은 화면에서만 정한다. 노드 배치(layout)는 캔버스가 정하므로 보내지 않는다.
- 노드는 {id, type, data} 이고 간선은 {id, source, target, kind} 이며 둘 다 일곱 종이다. 노드는 entry(입구, 정확히 1), agent(메인 1, 서브 0 이상), model(에이전트마다 1, 공유 가능), tools(0 이상), knowledge(0 이상, 공유 가능), memory(0 또는 1), guardrail(0 이상)이다. 간선의 방향은 붙이는 쪽에서 붙는 것으로 간다.

| kind | source → target | 규칙 |
|---|---|---|
| entry | entry → agent(main) | 정확히 하나 |
| model | agent → model | 메인·서브 모두 에이전트마다 정확히 하나. 한 모델 노드를 여럿이 공유할 수 있다 |
| tools | agent → tools | 메인·서브 모두 여럿 |
| knowledge | agent → knowledge | 메인·서브 모두 여럿. 노드 하나가 검색 Tool 하나가 된다 |
| memory | agent(main) → memory | 최대 하나 |
| guardrail | agent(main) → guardrail | 여럿. 거는 자리는 노드의 position 이 정한다 |
| delegate | agent(main) → agent(sub) | 메인에서만 나가고 순환 금지. 서브는 메인이 부르는 task Tool 이 된다 |

## 노드 data
- entry: session_ttl_seconds, max_turns, rate_limit{per_user_per_minute} 또는 null, max_concurrent_sessions, max_input_chars, greeting. 전부 기본값이 있다.
- agent: role(main 또는 sub), name(그래프 안에서 유일), description(서브는 필수이고 메인이 task Tool 설명으로 읽는다), system_prompt, context{compaction{trigger, keep}}(trigger 는 tokens·messages·fraction 중 하나, keep 은 messages·fraction 중 하나, 기본 fraction 0.85 와 0.1), max_tool_calls_per_turn, turn_timeout_seconds, retries, response_format("text" 또는 {json_schema: {...}}), language, builtin_tools{filesystem}(기본 true), skills[{id, revision}](붙인 Skill. list_skills 에서 permissions.consume 이 참인 Skill 의 id 와 그때의 최신 리비전을 적으면 그 리비전으로 고정된다. 에이전트마다 10개, 그래프 전체에서 서로 다른 Skill 20개까지이고 메인의 builtin_tools.filesystem 이 켜져 있어야 한다. 붙이지 않으면 키를 두지 않는다), code_execution{approval}(코드 실행. 메인에만 둔다. 있으면 Agent 가 대화마다 네트워크 없는 작업 공간에서 Python 과 셸 명령을 돌리고 파일 Tool 도 그 작업 공간을 쓴다. approval 은 ["approve", "reject"] 처럼 명령 실행 전에 물을 결정이고 비면 묻지 않는다. 끄면 키를 지운다. 메인의 builtin_tools.filesystem 이 켜져 있어야 하고, 클러스터의 격리 점검이 통과해야 배포된다. 작업 공간은 30분 동안 쓰지 않거나 대화가 닫히면 파일과 함께 지워지고, 거기서 만든 파일은 채팅 화면의 파일 서랍에서 내려받는다). 응답 형식이 JSON 스키마면 턴 끝 done 이벤트의 structured_response 에 결과 객체가 실리고, 스키마의 title 은 런타임이 structured_response 로 덮는다. 서브에이전트가 읽는 agent data 는 role, name, description, system_prompt, max_tool_calls_per_turn, turn_timeout_seconds, retries, skills 다. 응답 언어와 형식은 서브의 system_prompt 에 적고, 압축과 내장 파일 Tool 은 메인의 context 와 builtin_tools 를 따른다. 서브가 turn_timeout_seconds 를 넘기면 메인은 오류인 Tool 결과를 받고 턴을 잇는다.
- model: name(캔버스 표시용), provider(Platform Settings 의 provider 이름), model(비우면 provider 기본 모델), max_output_tokens, reasoning{effort: off, low, medium, high, xhigh, max 중 하나}, temperature(openai 만, anthropic 은 경고), fallback{provider, model} 또는 null. fallback 은 메인이 쓸 때만 걸린다.
- tools: source{kind: mcp_instance 또는 gateway_instance, id}, allow_tools[](비우면 배포 때의 전부), approval{Tool 이름: [approve, reject, edit, respond 중]}, timeouts{Tool 이름: 초}, read_only[](외부에 쓰지 않는다고 확인한 쓰기 Tool), allow_domains[]·block_domains[](웹 fetch 가 가도 되는·가지 않는 도메인). outside{Tool 이름: true 또는 false}(결과를 바깥 내용으로 다룰지를 기본값에서 바꾼 Tool. 우리 MCP Server 의 Tool 은 기본이 false, image·remote·entry 항목의 Tool 은 기본이 true). rememberable[](사람이 승인을 기억해도 되는 Tool. 기본은 비었다). allow_tools 의 이름은 그 소스(MCP Server 또는 Gateway)가 노출하는 Tool 이름이다.
- knowledge: knowledge_base_id, tool_name(기본 search_knowledge, 영문·숫자·밑줄 64자 이내), description(비우면 Knowledge Base 이름으로 만든다), top_k(1~20, 기본 5), min_score(0~1 또는 null). outside(검색 결과를 바깥 내용으로 다루는가, 기본 true. 검토를 거친 문서만 있는 Knowledge Base 는 false 로 둘 수 있다). Knowledge Base 를 만드는 법은 knowledge 안내에 있다.
- memory: checkpointer{data_service_id}, long_term{retention_days} 또는 null. Database 는 kind 가 postgres 또는 redis(Redis 8 이고 db 0. verify_data_service 의 redis.checkpointer 가 ready 여야 한다)이고 배포 클러스터와 같은 클러스터에 있어야 한다. memory 가 없으면 세션 상태가 파드 안에만 있어 재시작에 사라지고 레플리카끼리 공유되지 않으며, 배포 뒤 status.warnings 에 no_shared_state 가 붙는다. approval, rate_limit, service.budget.daily_tokens 중 하나라도 있으면 memory 가 필수다(memory_required). 장기 기억은 memory 노드에 long_term 을 두면 켜진다. /memories/ 아래 파일이 사용자마다 따로 세션 밖에 남고, retention_days 가 null 이면 만료가 없다. 그 memory 노드가 메인에 붙어 있고 메인의 builtin_tools.filesystem 이 켜져 있어야 한다.
- guardrail: position(input 은 사용자 말, output 은 에이전트의 글, tool 은 호출 인자와 결과를 본다), rules[{kind, value}], on_violation(기본 block, 또는 flag), message(막을 때 보이는 문구). kind 는 max_length(정수), deny_pattern(정규식), pii_mask({types[email, credit_card, ip, mac_address, url, regex 중], regex?}), injection_check({model, max_chars, max_calls})다. 정규식은 512자 이내이고 반복 안에 반복을 둘 수 없다(invalid_node_data). output 에 가리기나 막기가 있으면 답이 조각으로 흐르지 않고 메시지 단위로 한 번에 나온다. injection_check 는 판정 모델이다. position 이 tool 인 노드에만 오고(아니면 invalid_node_data) 그래프에 하나까지다(judge_count). model 은 같은 그래프의 모델 노드 id 이고(없거나 모델 노드가 아니면 unknown_judge_model) 그 노드는 간선 없이 붙은 것으로 친다. 메인과 모든 서브에이전트의 바깥 결과를 모델보다 먼저 판정 모델에 보여 숨은 지시가 있으면 block 은 결과를 막고 flag 는 이벤트만 남긴다. max_chars(기본 8000, 200~200000)보다 긴 결과는 앞과 뒤만, 한 턴에 max_calls(기본 20, 1~1000)번까지만 판정한다. 판정 모델은 모델 노드의 추론 강도와 상관없이 추론 없이(effort off) 부르므로 작고 빠른 모델(예: claude-haiku-5-5)을 쓴다. 판정 모델의 provider 도 평가의 채점 모델로 고를 수 있다.

## 제안 만들기
create_agent 와 update_agent 는 제안이다. 플랫폼이 검사한 뒤 사람이 승인 카드에서 고를 때만 저장되므로 ask_user 로 다시 묻지 않는다. 만들어 달라는 요청은 비슷한 Agent 가 있어도 create_agent 로 새 Agent 를 제안한다. 저장된 Agent 는 사람이 그 Agent 를 가리키거나 바꿔 달라고 할 때만 update_agent 로 바꾼다. 사람이 종류 없이 이름만 대면 list_agents 에서도 찾는다. 그 이름은 MCP Server 나 Gateway 가 아니라 Agent 의 이름일 수 있다.
1. 필요한 묶음을 한 번에 연다(agent, mcp, gateway, skill, knowledge, data, settings). 모델은 Platform Settings 의 provider 에서, Tool 소스는 배포된 MCP Server 와 Gateway 에서 고른다(draft 는 소스가 될 수 없다). Tool 은 이름과 validate_agent_graph 의 tool_effects 로 고르고, 읽을 수 없는 바깥 항목의 설명을 근거로 삼지 않는다.
2. 새 Agent 는 list_agent_templates 의 support-agent 에서 시작해 모델 노드의 provider, tools 노드의 source, memory 노드의 data_service_id 를 채운다. Database 는 list_data_services 에서 배포 클러스터와 같은 클러스터의 것을 찾는다(postgres, 또는 checkpointer 가 ready 인 redis db 0). 배포된 MCP Server 를 쓸 때는 source.kind 를 mcp_instance 로(런타임 계약의 이름이다), id 를 그 MCP Server 의 id 로 바꾸고 allow_tools 와 approval, timeouts 를 그 Tool 이름으로 고친다. create_agent 에는 {name, display_name, graph, service} 를 보낸다. 같은 이름이 있으면 저장 때 409 name_conflict 이고 name 은 나중에 바꿀 수 없다.
3. 보내기 전에 짠 graph 를 validate_agent_graph 로 검증한다. 더하거나 바꾸는 tools 노드마다 allow_tools 에 Tool 이름을 적고(비우면 empty_allow_tools 로 거절된다), 검증 결과의 tool_effects 가 write 인 Tool 마다 approval 을 ["approve", "reject"] 로 둔다. 바꾸는 tools 노드에 있던 approval 은 지우지 않는다. 사람이 승인을 빼 달라고 하면 제안에서 빼지 않고 캔버스에서 직접 빼라고 말한다. 승인과 entry.rate_limit, service.budget.daily_tokens 는 memory 가 있어야 한다(memory 줄). 쓸 수 있는 Database 가 있으면 memory 노드에 그 id 를 넣고, 검증 오류를 피하려고 memory, approval, rate_limit, daily_tokens 를 빼지 않는다. 쓸 수 있는 Database 가 없을 때만 쓰기 Tool 을 allow_tools 에서 빼고(승인 없이 넣지 않는다) memory 와 rate_limit, daily_tokens 도 뺀 제안을 create_agent 나 update_agent 로 보낸다. 그 뒤 뺀 쓰기 Tool 을 말하고, 그 Tool 을 쓰려면 Database 를 먼저 더해야 한다고 제안한다.
4. 사람이 말한 것만 바꾼다. Skill 을 붙일 때 system_prompt 에 그 Skill 을 적지 않는다. 런타임이 붙인 Skill 의 이름과 설명을 모델에게 알린다. Skill 은 사람이 이름을 댔거나 이름과 설명이 맞고 consume 할 수 있는 것만 붙인다. read_only, rememberable, outside 는 사람이 캔버스에서 다는 표시라 넣거나 늘리지 않는다(person_marks_only).
5. 저장된 Agent 를 바꿀 때는 get_agent_definition 으로 개요(node_id 없이)를 읽고 바꿀 노드를 하나씩 읽은 뒤 update_agent 에 바뀌는 것만 보낸다. set_nodes 는 노드를 id 로 통째로 더하거나 바꾸고(읽은 data 전체를 고쳐 보낸다), remove_nodes 는 노드와 그 간선을 지우고, add_edges·remove_edges 는 {source, target, kind} 로 간선을 더하고 지우고, set_service 는 service 칸을, set_display_name 은 표시 이름을 바꾼다. 읽지 않은 노드는 보내지 않는다. system_prompt 같은 긴 글은 읽은 전문을 고쳐 보내고 줄이거나 요약하지 않는다.
6. 제안을 보낸 뒤 그 제안이 하는 것과 뺀 것을 몇 줄로 말한다. 다듬어 달라는 메시지를 받으면 새 제안을 짠다. 카드에서 거절되면 사유를 반영해 새 제안을 짜고, 사유가 없으면 무엇을 바꿀지 묻는다. 새 제안은 저장된 리비전 위에서 짠다(만들기는 앞 제안의 graph 에서 시작한다). 앞 제안이 저장되지 않았으면 사람이 빼라고 하지 않은 앞 제안의 변경을 모두 다시 넣는다. 사람이 캔버스에서 직접 저장해 제안이 닫혔으면 한 줄로 받아들이고 다시 제안하지 않는다.

## 배포와 그 뒤
- deploy_agent 에 {cluster_id?, namespace?, replicas?, resources?, exposure?} 를 보낸다. 승인이 필요하다. 현재 리비전이 핀되고 클러스터 리소스 이름은 agent-<name> 이다. draft 가 아니면 409 already_deployed 다. 바꾼 정의는 redeploy_agent 를 불러야 떠 있는 파드에 반영된다.
- get_agent 을 반복해 status.phase 가 Ready 가 될 때까지 기다린다. Pending 과 Rolling 은 기다리고 Failed 면 status.message 와 status.error 를 읽는다. undeploy_agent 는 클러스터에서만 내리고 정의와 장기 기억을 남기므로 같은 id 로 다시 배포된다. delete_agent 는 정의와 장기 기억까지 지운다.

## 채팅과 승인
- Ready 뒤 채팅은 화면 /agents/<id> 에서 하고 API 경로는 status.chat_url 이다. 비서는 채팅·승인 결정·중지를 대신 부르지 않는다. 새 세션의 첫 SSE 이벤트는 greeting{session_id, text} 다. entry.greeting 이 비어 있지 않을 때 새 세션에서만 나오고 모델에게는 들어가지 않는다. 글은 status.greeting 과 같은 배포된 리비전의 것이라 정의만 고치고 재배포하지 않으면 옛 글이 나간다.
- 승인이 걸린 Tool 호출은 사람이 approval 에 적은 결정(approve, edit, reject, respond) 가운데 하나로 푼다. edit 은 같은 Tool 의 인자만 고친다. Tool 이름을 바꾸면 422 edit_name_mismatch 이고 세션은 승인 대기 그대로다. 고친 인자도 position 이 tool 인 가드레일을 지나므로 block 이면 422 guardrail_blocked 이고, flag 면 재개 스트림 앞에 guardrail 이벤트가 온다. 진행 중 턴은 POST /api/agents/<id>/sessions/<sid>/cancel 로 멈추고 화면의 중단 단추가 이것을 쓴다. 멈춘 스트림은 error{code: turn_cancelled} 로 끝난다. 진행 중 턴이 없으면 409 no_turn_in_progress 이고, status.runtime.features 에 cancel 이 없으면(runtime 이 null 이어도) 409 runtime_feature_missing 이다.

## 오류 코드
| code | 뜻 |
|---|---|
| entry_count, main_agent_count, model_count, memory_count | 개수 규칙 위반. model_count 는 모델 간선이 0개이거나 2개 이상인 에이전트다 |
| dangling_edge, invalid_edge_kind, delegation_cycle, unreachable_agent, duplicate_node_id, duplicate_edge_id, duplicate_agent_name | 간선이 없는 노드를 가리키거나 조합이 표에 없거나, 위임이 순환하거나 entry 와 이어지지 않는 에이전트가 있거나, 노드·간선 id 나 에이전트 name 이 겹친다 |
| unknown_provider, provider_no_key, unknown_judge_model, judge_count | 모델 노드나 Knowledge Base 임베딩의 provider 가 등록돼 있지 않거나 키 Secret 이 비어 있다. stub 은 키가 면제된다. injection_check 의 model 이 비었거나 같은 그래프의 모델 노드가 아니거나, 판정 규칙이 그래프에 둘 이상이다 |
