# Daegam agent-runtime

The fixed image every Agent pod runs (D26). The init container puts `/config/agent.json` in place (its contract is
[schema/agent.schema.json](schema/agent.schema.json)); the runtime builds a LangChain `deepagents` graph from it and
serves SSE chat and session reads on `:8080`.

This README answers:

1. Which module does what?
2. Which routes does the runtime serve, who may call them, and what does each one answer?
3. Which SSE events and which observability events does it emit?
4. Which feature names does an image know, and how do init and the startup check use them?
5. How are attached Skills fetched and shown to the agent?
6. Which environment variables does it read, and how is it developed and run locally?

This README is the home of the runtime's API, its SSE and observability events and its feature names. The guides
`agents.md`, `chat.md` and `knowledge.md` that the sections below name are the maintainers' documents and are not part
of this repository's public tree.

## Modules

| File | What it does |
|---|---|
| `runtime/main.py` | The entry point. Builds the FastAPI app and opens resources through `boot.py`. Two middlewares sit inside CORS, so their refusals carry CORS headers on the exposed path: `RefusingMiddleware` answers every request but `/healthz` with 503 while chat cannot be served (a document with an unknown feature name, D65; a store not opened yet, T22), and `BodyLimitMiddleware` cuts request bodies at 24 MiB (`MAX_CHAT_BODY_BYTES`) with 413 `payload_too_large`, from `Content-Length` or while reading |
| `runtime/error_codes.py` | The error code registry (P74, D86): `STATUS` gives each code its one status and `RECORDED` the few codes with more, each with its reason. `status_of` is the lookup for rewraps (only single-status codes). Under tests (`STRICT`, set by `tests/conftest.py`) the HTTPException handler checks every answer against it; `tests/test_error_codes.py` scans `runtime/` for raise sites, and the platform's `test_error_code_parity.py` compares shared codes |
| `runtime/boot.py` | Opens the session store, knowledge, long-term memory, tool sources and a verifier per issuer, in that order, builds `RuntimeState` and starts the background tasks (tool refresh loop, session sweep, the one expired long-term memory sweep). Start-up when a store or a tool server is not there yet is in agents.md section 5. Any other error on the first attempt is a configuration error: the reason goes to `/dev/termination-log` and the start fails. Background retries wait a random time in [interval/2, interval], starting at 2 s and doubling up to 30 s (`next_retry`) |
| `runtime/config.py` | Loads `agent.json` (path override env `DAEGAM_AGENT_CONFIG`), validates the schema and the references (tool refs, unique sub agent names, and with the feature `skills` unique Skill names and per-agent names that exist). Unknown names in the document's `features` are caught before schema validation, and the runtime then starts without taking chat (section "Feature names and init steps"). `ConfigError` lists every start-up error code the runtime can give; the codes are a contract read by the start log and the platform's warning display |
| `runtime/features.py` | The feature names this image knows: document features `DOCUMENT_FEATURES`, runtime capabilities `CAPABILITIES`, their union `KNOWN` (D65). The init fetch script reads only this module, so it uses only the standard library |
| `runtime/init_steps/` | The init steps of document features. After the init container fetched `agent.json`, it calls `run(config_dir, fetch)` of `runtime.init_steps.<name>` for every name in `features` that has such a module. The only step today is `skills.py` (section "Skills") |
| `runtime/models.py` | Builds a `BaseChatModel` per provider kind; the field mapping and the Claude reasoning table are in agents.md section 3. Keys come only from the pod env that `provider.env_key` names. The SDK clients are the shared hooked clients of `llm_http.py` (an `http_async_client` for openai, `HookedChatAnthropic` for anthropic), openai models ask for streaming usage unless the provider has `stream_usage: false`, and each model's `metadata` carries `daegam_provider`, `daegam_route` (`gateway` when the provider has `gateway: true`) and `daegam_role` (`main`, `fallback`, `subagent`, `guard` for the judge model) for the tracer (P37). A model whose client lacks the hook is the state warning `correlation_hook_missing` in `/healthz`, `runtime_start` and `/metrics` (so also in the Agent status), which does not block start-up. The quota test `quota_exhausted` (T20) lives in `llm_http.py`. `harness_key` keeps a `:` on the model side, so fine-tuned names (`ft:…`) compile |
| `runtime/stub.py` | The deterministic stub model (agents.md section 3). It reads only the text blocks of a user message; when the request's human message has image blocks, a text answer ends with `(이미지 n개를 받았습니다)`, where e2e checks that attached images reached the model request. With nothing to call it answers `Tool 이 없어 답만 합니다: <input>` |
| `runtime/tool_names.py` | The names of tools deepagents and langchain add by themselves (`FILESYSTEM_TOOLS`, `SUBAGENT_TOOL`, `STRUCTURED_RESPONSE_TOOL`, `BUILTIN_TOOLS`, `builtin_tools_for`, `CODEX_MODELS`). Compilation, translation and the stub read them; the built-in names each agent actually gets come from `compile.builtin_names`. A platform test loads this file and compares it with `RESERVED_TOOL_NAMES`, so the file uses only the standard library |
| `runtime/compile.py` | `create_deep_agent(...)` with the handling of deepagents defaults described in agents.md section 2. Tools are the MCP tools and the knowledge search tools joined; a name that appears twice is `tool_name_conflict`, and a source tool named like one of the agent's built-in tools (`builtin_names`, read from what deepagents adds for that agent's model) is dropped with the status warning `builtin_tool_name`. The main agent's `middleware` list is compaction, the Skills middleware, the tool call limit, `SubagentTimeout` (with sub agents), the guardrails, the session budget, fallback, retry and last `AttachmentImages`, so images are filled inside fallback and retry on every attempt. The file backend is always a `CompositeBackend` (`build_backend`): the session's `StateBackend` by default, `/uploads/` as `UploadsBackend`, plus `/memories/` with long-term memory and `/skills/` with Skills. The file tool rules of `permissions.py` go to the main agent and sub agents inherit them. With long-term memory on, a second graph without the `/memories/` route serves ephemeral turns |
| `runtime/guards.py` | `guardrails[]` by position: `input` at the `/chat` entrance (`InputGuard`), `output` in `after_model` (`OutputGuard`) plus `OutputFilter` on the text the stream emits, `tool` in `wrap_tool_call` (`ToolGuard`). The rule `injection_check` is parsed here and run by `judge.py`. Behaviour is in agents.md section 4. Attachment text is checked by `InputGuard` without the `max_length` rule, and a violation carries the attachment's name. Violations go out as the custom stream signal `guardrail{position, rule, action}` |
| `runtime/budget.py` | `service.budget.session_tokens`. `after_model` adds `usage_metadata` to the thread state `daegam_tokens` and ends the turn with `jump_to=end` when the budget is passed |
| `runtime/resilience.py` | `limits.retries` as `ModelRetryMiddleware`, `main.fallback` as `ModelFallbackMiddleware` (rules in agents.md section 3), and `SubagentTimeout`, which applies a sub agent's `limits.turn_timeout_seconds` to its `task` call and hands the main agent a `status="error"` tool result past it. Env `DAEGAM_RETRY_INITIAL_DELAY_SECONDS` lets tests shorten the first wait |
| `runtime/signals.py` | The signals middleware sends to the runtime through langgraph's custom stream (`guardrail`, `budget`, `model_fallback`, `model_retry`, `tool_limit`, and the stdout-only `web_guard` and `injection_check`) |
| `runtime/tool_limit.py` | `limits.max_tool_calls_per_turn` as `TurnToolLimit`, a `ToolCallLimitMiddleware` per run on the main agent and every sub agent (T82). The first calls past the limit do not run and get a tool result telling the model to answer with what it has; the model is called once more and answers. Calls after that notice end the turn with no text added; a sub agent stopped this way leaves the main model a `task` result saying so, in an AIMessage marked `daegam_hidden` that the stream never shows. The structured response tool is never counted or refused. The first crossing emits `tool_limit` |
| `runtime/judge.py` | The judge layer for documents with the feature `injection_check` (P43): one `InjectionJudge` per agent, the main agent and every sub agent, between the web guard's outer layer and `ToolGuard`. It shows each result with an outside mark to the judge model (role `guard`, langchain's internal-call metadata, effort as compiled) with a fixed English prompt, after dropping the lines our layers add (`source_text`). `INJECTION` blocks the result (`injection_blocked`, artifact emptied) or flags it; a timeout of 10 s, a failure, a refusal, an answer without a label and every result past `max_calls` pass as outside content with the event `injection_check`. `JudgeCalls` in `TurnContext` counts the run's judge calls for the main agent and its sub agents together |
| `runtime/hitl.py` | Reads pending approvals from the checkpointer and validates decisions before `Command(resume=...)` (the `/decisions` row below) |
| `runtime/mcp.py` | One `langchain.mcp` `MCPAdapter` (streamable-http) per tool source (T6). Auth is `oauth_client_credentials` (an `httpx2.Auth` that adds the token per request and renews it 60 s before expiry), `bearer` (a fixed token from the pod env, the platform's service token, D41) or none. `tools/list` waits at most 15 s per source (`TOOLS_LIST_TIMEOUT_SECONDS`); if any source cannot be read the listing fails with `tools[<ref>]: <reason>`, and `ready` is true only after every source was read once (T18). The client uses fastmcp's default `mode="auto"`, records the protocol version each listing connection settled on in `protocols`, and declines server requests for user input (elicitation). The `allow` filter, per-tool timeouts and the 5-minute refresh are in agents.md section 2 |
| `runtime/knowledge.py` | Turns `knowledge[]` into search tools (D32, knowledge.md section 4). Embedding and database errors become a `status: error` tool result instead of ending the turn. The SDK does not retry (`MAX_RETRIES = 0`); a transient embedding error is retried once with a new call id, each request carries the run's `traceparent`, and each attempt reaches the tracer as `daegam.embeddings` (P37) |
| `runtime/agent_calls.py` | Turns each `tools[]` entry whose `source.kind` is `agent` into one Tool `ask_*` with the argument `message` (feature `agent_tools`), built from the entry alone, so nothing is listed and the pod is ready without an answer from the platform. `AgentCall.run` starts a run of the called Agent with `POST <url>` `{message}`, asks `GET <url>/runs/{run_id}?wait=<seconds>` until the run settles, and retries a failed poll but never the start; no request lasts over 30 s. Past `timeout_seconds`, or the calling turn's remaining time when that is shorter, it sends `POST <url>/runs/{run_id}/cancel` `{reason: caller_timeout}` and answers a Tool error that says so; a stopped turn sends the same with `caller_ended`. Each request carries the turn grant's token for the target `(agent, <called Agent id>)`, or, in a turn whose grant holds no such token, the instance token with `X-Daegam-Caller-Session`, `X-Daegam-Caller-Turn` and `X-Daegam-Caller-Owner` (percent-encoded); an expired token sends nothing. `X-Daegam-Caller-Outside` says whether the session holds outside content. A finished run answers its text with `run_id` in the artifact's `structured_content`, a run waiting for an approval answers a fixed text at once, and a run that ended without an answer or a call the platform refused is a Tool error with the code. Entries with `mode: task` get no `ask_*` Tool; `CallSender` (the credentials of a request) and `refused` (the Tool error of a refused request) also serve their Tools |
| `runtime/agent_task_tools.py` | The five task Tools that all `tools[]` entries with `source.kind: agent` and `mode: task` share on the main agent: `start_async_task`, `check_async_task`, `update_async_task`, `cancel_async_task` and `list_async_tasks`, with the names, argument schemas, descriptions and graph state `async_tasks` of deepagents' async sub agent Tools (`tests/test_agent_task_tools.py` compares them with the locked package). The model picks the called Agent by `subagent_type`, which is the entry's `source.name`. The entry's `url` is the called Agent's Agent Protocol path on the platform: a start sends `POST <url>/threads` `{}` and `POST <url>/threads/{thread_id}/runs`, a check `GET .../runs/{run_id}` and, after `success`, `GET <url>/threads/{thread_id}`, an update one more run with `multitask_strategy: interrupt`, a cancel `POST .../runs/{run_id}/cancel?wait=0&action=interrupt` without a body, and a list one `GET .../runs/{run_id}` for each task that is not final. The requests go through the runtime's own HTTP client with the credentials of an `ask_*` call on each request, not through `langgraph_sdk`. Unlike deepagents' Tools, a refused request is a Tool error with the platform's code, an answer that cannot be read after `success` is a Tool error, an answer without `thread_id`, `run_id` or `status` is a Tool error, the `running` filter also lists `pending` tasks, a check reads `error` for `cancelled` too, and a check result keeps non-ASCII text as it is. The Tools never check a task by themselves. `AsyncTaskState` puts `async_tasks` into the main agent's state; a sub agent that points at such an entry stops the compile with `agent_task_not_main` |
| `runtime/stub_embedding.py` | The stub embedding, byte-identical to the platform's `platform/daegam/services/knowledge/stub_embedding.py`, so indexing and searching produce the same vectors |
| `runtime/dsn.py` | Resolves `dsn_env` (`<PREFIX>_URL`) and the separate env vars of the same prefix (`<PREFIX>_HOST/PORT/...`) into a psycopg conninfo or redis client arguments, preferring the separate vars; memory and knowledge use the same rule. Also checks a store at start and splits failures into not reachable yet (`*_unreachable`, T22) and refused after connecting (`*_rejected`, T23); the start waits for both (`is_waitable`); `redis_prefix` and `turn_lease_key` name the Redis keys the index, the transcripts and the lease checks share |
| `runtime/sessions.py` | The checkpointer and the session index (D26, D33). Postgres: `AsyncPostgresSaver`, the index table `daegam_sessions` (a row per session with `instance_id`, so instances sharing a Database never see each other's sessions in lists, counts, totals or the sweep) and the shared counters `daegam_counters`. No memory node: `InMemorySaver` with an in-memory index and counters, the warning `no_shared_state`, and limits that loosen by the replica count. The sweep runs once right at start and then every minute on the index, looks at two times (chat.md section 4) and deletes expired counter rows each time; a pod woken after a sleep therefore closes the sessions whose TTL passed meanwhile without waiting a minute (P44). The index keeps the instance's drain mark (P44): the table `daegam_drains` on Postgres, the key `drain` on Redis, a field in the pod without a memory node, each holding the mark id the platform picks for one sleep and its deadline. `SessionIndex.mark_drain` sets it for 120 s, replacing an earlier mark and its id, and counts the instance's live leases in the same step, and while it stands every `claim_turn` and `claim_delete` raises `DrainMarked` and writes nothing. `SessionIndex.clear_drain_mark` deletes the mark only when its id matches, so a late clear from an earlier sleep leaves a newer mark in place. On Postgres a claim runs in a transaction that first takes an advisory lock derived from the instance id in shared mode and then reads the mark, and the mark takes the same lock exclusively before it writes and counts, so a claim either commits before the count or sees the mark. A start never clears the mark; it expires or the platform clears it. The index row carries five turn record fields (`title`, `turn_id`, `last_turn`, `upload_bytes`, `cite_seq`); the integer ones are `NOT NULL DEFAULT 0`, so an older runtime sharing the Database still inserts, and list and detail rows carry only `title`. Deleting a session removes the checkpoints, the attachments, the transcript and the index row, in that order; a first-turn regenerate that deletes the thread (`delete_checkpoints`) keeps the attachments |
| `runtime/session_index_redis.py` | The session index on Redis 8 (sorted sets and hashes) and opening the checkpointer `ChainRedisSaver`; every key is under `daegam-agent:{instance_id}:` (the key layout is in agents.md section 4). The checkpointer's `adelete_thread` removes at most 10,000 checkpoints and 10,000 writes per call, so `delete_redis_thread` repeats it until both RediSearch indexes count no document of the thread (at most 20 rounds, then `CheckpointsRemain`), counting with the same redisvl tag filter (`CountQuery`). A prefix SCAN cannot tell, because `write_keys_zset:*` sits outside the prefix. A title search over an approver's full list reads the recent-first set 200 rows at a time and stops when it has `limit` rows or after 10,000 rows. The drain mark is the key `drain` with an expiry and the mark id as its value: the claim script checks it before anything else, the mark script sets it and counts the members of `turns:open` that still hold a lease key, in one script, and the clear script deletes it only when the value is the given id. The mark script builds those lease key names itself instead of receiving them as keys, so it works only on a single Redis, not on Redis Cluster or a cluster-mode proxy |
| `runtime/redis_saver.py` | `ChainRedisSaver`: `AsyncRedisSaver` with its own `aget_delta_channel_history` (D72), so a state read rebuilds the delta channels in a fixed number of round trips (six for a session without files, five with; the bound is in the module docstring) instead of one `aget_tuple` per checkpoint of the chain. A session that has written files fewer than 50 times still reads its whole chain for `files`, in the same round trips. How it reads and what it costs are in agents.md section 4; `tests/test_redis_saver.py` compares it with the base walk, counts the round trips of `graph.aget_state` and fails when a lock bump brings the upstream method |
| `runtime/transcript.py` | The screen transcript next to the session (chat.md section 4): `daegam_transcripts` on Postgres, a list under the instance prefix on Redis, a dict in the pod without a memory node. Writes are appends only; at most `TRANSCRIPT_LIMIT` (500) items, the oldest dropped first. `apply_event` follows the same rules as the UI's `applyChatEvent` |
| `runtime/turn_record.py` | Turn records (P36): session titles, turn attempt numbers and ids (chat.md section 2). The three title limits (`SESSION_TITLE_MAX_CHARS`, `AUTO_TITLE_MAX_CHARS`, `SESSION_TITLE_RAW_MAX_CHARS`) are compared by a platform test with the platform's and the UI's values, so the module uses only the standard library. Each `TurnAttempt` gets a `turn_id` (uuid4 hex, 32 characters) written to the index's `turn_id` and `last_turn` right after the lease is taken; a decision resume continues the same number and id, and the human message that opens a turn has the id `u-<turn_id>` |
| `runtime/sessions_api.py` | The owner's session management: `PATCH` and `DELETE /sessions/{sid}`. Owner only; the approver header does not pass |
| `runtime/memories_api.py` | Viewing long-term memory and deleting one file: `GET /memories`, `GET` and `DELETE /memories/files/{key}`. Reads only the caller's own namespace in the store already open; deleting removes one store key, not `StoreBackend`'s prefix delete |
| `runtime/session_files.py` | Session file list and download: `GET /sessions/{sid}/files`, `GET /sessions/{sid}/files/{path}`. Under `/uploads/` it reads the attachment store, otherwise the checkpoint's `files` channel, and leaves out deepagents' internal paths |
| `runtime/downloads.py` | The five download headers. The second copy of the platform's `platform/daegam/api/_download.py` rules; both sides' tests compare against `schema/fixtures/chat/download-headers.json` |
| `runtime/regenerate.py` | Regenerate and message edit: `POST /sessions/{sid}/regenerate` (chat.md section 5). After taking the turn lease it walks the parent chain back from the newest root checkpoint (`checkpoint_ns: ""`) to the first `source: input` checkpoint and branches from its parent; only a first turn, whose input checkpoint has no parent, deletes the thread and runs again. The question is read from that checkpoint's input channel (`__start__`). The work inside the lease is split into `_plan` (read and judge) and `_commit` (count, delete the thread, write the index). A discarded branch stays in the checkpointer until the session closes (on Redis about 75 KB per run), so one turn can be regenerated 10 times a day (UTC) |
| `runtime/fork.py` | The regenerate branch (`Fork`) and reading the root namespace's head. The turn run in `turn.py` carries the `Fork` and, when it finishes the turn, sees a branch when the newest root checkpoint differs from the one at the start |
| `runtime/lease_keeper.py` | The turn lease keeper (P79, D98): one per pod, started after the session store and stopped after the drain's settlement. It renews every lease it holds by token every 10 s in one round (`SessionIndex.renew_turns`; Postgres on a connection of its own outside the pool with `lock_timeout` 3 s, Redis and the in-pod index through the index), abandons a round with no answer by the earlier of 10 s and the leases' earliest fence, retries after 5 s, moves each confirmed lease's fence to 45 s after the round's send, and loses a lease that is gone or past its fence, which stops its turn (`HeldLease.on_lost`) |
| `runtime/fence.py` | The fence of a turn that lost its lease (P79 section 2): the turn's `Fence` in a context variable from the claim on, checked where bytes leave the process: the Redis connection class swapped into the session and uploads clients (before connecting and right before writing a command; the handshake and health check run outside the fence), `FencedCursor` on the session pool (each statement bound by the fence's deadline, which follows the keeper), `FencedPostgresSaver` (the pipelined checkpoint writes as one block), `FencedStore` for `/memories` writes. A refused write is `TurnFenced`; `refused()` is what a token-checked write raises when the server refuses it, which also drops the lease |
| `runtime/turn_repair.py` | The repair of a turn that ended without releasing its lease (P79 section 3, D98). A session row whose lease lapsed while its open mark stayed carries that token as `orphan`, and a claim refuses it. The session read (`turn_gate.py` `load_session`), the sweep and a session delete repair it, at most two at once per pod (`REPAIR_SLOTS`); reads leave a failed one alone for 10 s and the sweep waits for a slot. The checkpoint is read first without a lock, then the index writes in one transaction under the row lock or one Redis script (`SessionIndex.repair_turn`): the status from the checkpoint (a closed session stays closed), the marks cleared, and a `turn_aborted` line, after a user item rebuilt from the checkpoint for a chat that saved none (`repair_items`). Only the writer emits `turn_end{status: turn_aborted, repaired: true}`, from the run marker it read. `align_with_checkpoint` moves a session blocked before P79 between `active` and `pending` |
| `runtime/background.py` | `stop_tasks`, which cancels background tasks and waits for them; used by the boot's tasks and the lease keeper |
| `runtime/turn_gate.py` | Turn entrance checks and the turn lease, used in the same order by `/chat`, `/decisions`, regenerate and session management: the request check `check_request` (tools ready, rate limit, input length and input guardrails, daily budget), the session checks (`check_open_session`, `check_session_budget`), the edited arguments of a decision (`check_decision_args`), the 60 s lease `held_lease` (handed to the lease keeper, the work inside runs in its fence, released only when that work fails, answered 503 when the fence stops it, and 503 `agent_draining` when the drain mark refuses the claim) and `note_attempt`. A new session checks the drain mark in `check_request` before its row exists. `load_session` reads an open session whose last turn is older than the session TTL and that no live lease holds as `closed`, without writing, and `check_still_open` checks the TTL again under the turn's own lease, so a session that expired while the Agent slept takes no turn, decision, pending read or file read before the first sweep closes it (P44 section 11). `check_caller` (who may see a session) and `checked_file_key` (file path rules) are here too, shared by the session file and memory file routes |
| `runtime/citations.py` | The citation ledger (chat.md section 7). Search tools get a session-wide number `cite` per result, starting after the index's `cite_seq`; the same chunk within a turn keeps its number. The ledger rides in the turn context (`TurnContext`), shared by the main agent and sub agents, and the last number is written to the index when the turn ends, even with an error. Sources go in the tool result's artifact, which the model does not see, without the text |
| `runtime/tool_safety.py` | Tool traffic safety for documents with the feature `tool_safety` (P43, D96). Each agent gets the block wrapper, the outermost tool layer, which refuses remembered rejects and calls that cannot be approved (`ToolBlock`); the outside wrapper, the innermost tool layer, which wraps and marks results from outside (`OutsideMarks`); and the verdict layer, a model-call layer outside fallback and retry that stores a verdict for every call of the AI message it returns (`ToolVerdicts`). It also builds an approval entry for every tool, whose `when` reads only the stored verdicts, and the history scan run when a turn opens |
| `runtime/outside.py` | The `<outside_content>` wrapper and its escaping, the session's outside flag (`OutsideFlag`, written once to the index as `outside_at` and failing closed), and the per-`task` record of a subagent's outside reads |
| `runtime/runs.py` | The background run session rules (P41 section 9): the shape of the run fields of `/chat` (`check_run_fields`), 409 `run_exists`, the decision check (`check_run_decision`) and `X-Daegam-Run-Id`. The turn side (ephemeral turns, `untrusted`, closing) is in `turn.py`. It also holds the task session rules (capability `agent_tasks`): `task` of `/chat`, the next run of a task session (`take_next_run`) and which run sessions close at a turn's end (`runs_once`) |
| `runtime/approvals.py` | The remembered choices a turn carries (`approval_choices`), the pending request used to resume a message that has no stored verdicts (`PendingCalls`), and the reason line of an approval request |
| `runtime/long_term.py` | Long-term memory (D34, agents.md section 8). With `memory.long_term` the file backend gets the route `"/memories/": StoreBackend(...)` to the store in the checkpointer's Database. The turn context `TurnContext` carries the owner, the citation ledger and the turn's attachments, and for `tool_safety` documents the session's outside flag, the turn's remembered choices and the pending request of a resume, and the run's judge call count (`judge_calls`). The namespace is `(tenant, instance_id, sha256(session owner sub))`; Postgres uses the schema `daegam_store` (the platform creates it, a missing one fails the start), Redis `store_prefix=daegam-agent:{instance_id}:store`. After the start a background task deletes expired memories once (`LongTermMemory.sweep_expired`, the store's `sweep_ttl`), because the Postgres store's own sweeper waits a whole interval of 60 minutes before its first sweep; it does not hold the readiness probe, on Redis the call returns 0, and a failure is only logged |
| `runtime/counters.py` | The counters for requests per user per minute (`entry.rate_limit`), daily tokens (`service.budget.daily_tokens`) and regenerations per turn. Postgres increments atomically with one statement `INSERT ... ON CONFLICT (key) DO UPDATE SET value = value + EXCLUDED.value RETURNING value`; Redis with `INCRBY` and `EXPIREAT` in one MULTI under the instance prefix. Keys are `<instance id>:rate:<user_sub>:<YYYYMMDDTHHMM>`, `<instance id>:tokens:<YYYYMMDD>` and `<instance id>:regen:<session id>:<turn>:<YYYYMMDD>` (fixed UTC windows) |
| `runtime/stream.py` | Turns `astream(stream_mode=[messages, updates, custom], subgraphs=True)` into SSE events. The turn timeout is `asyncio.timeout`. `astream` runs in a separate task (`_relay`), so a timeout or a stop stops the graph and waits for it to finish. A continuing turn seeds its state from the checkpoint's messages (`TurnState.seeded`), so history tool events and usage are not emitted again |

## API

Every error body is `{"code": ..., "message": ...}`. Each code has one status, listed in `runtime/error_codes.py`
(P74, D86); the codes with a recorded second status are `not_pending` (404 on `GET`, 409 on the decision) and `error`
(the name of an uncoded answer, any status). An Agent deployed with a runtime image older than this release answers
413 `body_too_large` for an oversized body until it is redeployed. There are two inbound paths, and every handler looks
at one `Caller` instead of the body's `user_sub`.

A body or query that fails a request model is 422 `validation_error`, the platform's code for the same case:
`{"code": "validation_error", "message", "errors": [{loc, msg, type}]}`, with at most 50 entries and the count of the rest in `more_errors`. `message` joins the entries as `loc: msg`
with `; ` (each `loc` joined with `.`), the text the platform's screens make from their own validation errors. The
rejected value is never echoed: `input` and `ctx` are dropped, and a type whose message would quote the value
(`union_tag_invalid`, `value_error`) gets a fixed message (`runtime/validation.py`). It is not counted as a refused
turn.

| Path | Credential | `Caller` |
|---|---|---|
| Platform proxy | `Authorization: Bearer <DAEGAM_INSTANCE_TOKEN>` | `sub` is the POST body's `user_sub` (absent: 422 `user_sub_required`) or the GET query `user_sub`; `external = false`; `approver` is `X-Daegam-Approver: 1` |
| External (Ingress) | `Authorization: Bearer <OIDC access token>`, only when `DAEGAM_OIDC_AUDIENCE` (the data plane audience) and an issuer (`DAEGAM_OIDC_ISSUER`, `DAEGAM_IDP_ISSUER`) are set | `sub = claims.sub`, `external = true`, `approver = false` (the header is ignored). The body's `user_sub` is ignored |

The instance token is judged first; otherwise a JWT-shaped value (two dots) goes to the verifier its `iss` picks (Two issuers below); anything else is 401
`unauthorized`, so a stale instance token never shows up as `invalid_token`. A local run without
`DAEGAM_INSTANCE_TOKEN` treats every request as the proxy path. External path rules: `GET /sessions` is fixed to the
token's own `sub`; `GET /sessions/{sid}`, `GET /sessions/{sid}/pending`, `POST /sessions/{sid}/decisions`,
`POST /sessions/{sid}/cancel`, `PATCH /sessions/{sid}`, `DELETE /sessions/{sid}`, `POST /sessions/{sid}/regenerate`,
`GET /sessions/{sid}/files` and `GET /sessions/{sid}/files/{path}` are for the session owner only (403
`not_session_owner`); `GET /memories` and `GET` and `DELETE /memories/files/{key}` serve only the token `sub`'s memories;
`GET /metrics` is 403 `forbidden`; `GET /healthz` gives only `{"status": "ok"}`. Browser clients cannot use
`EventSource` (no POST, no `Authorization` header), so they read the SSE with `fetch` and a `ReadableStream`.

**Two issuers (capability `two_issuers`, P53b).** External tokens come from up to two issuers, each with its own
verifier and rules: the issuer the data plane trusts (`DAEGAM_OIDC_*`, `DAEGAM_ALLOWED_GROUPS`,
`DAEGAM_AGENT_CLIENT_IDS`) and an IdP beside it (`DAEGAM_IDP_*`), which the platform renders for exposed Agents of an
oidc install that trusts the platform. Both check the audience `DAEGAM_OIDC_AUDIENCE`. The token's `iss`, read before
the signature, picks the verifier, which then checks the issuer, signature and audience with its own keys: a token that
names one issuer and is signed with the other's keys is 401 `invalid_token`, and one whose `iss` names neither is 401
`invalid_token` without a JWKS fetch. Each issuer's groups claim, client-id claim, allowed groups and client ids judge
only its own tokens. The first issuer is the platform when `DAEGAM_OIDC_JWKS_URL` is set or an IdP is configured beside
it (`runtime/auth.py` `read_issuers`); the platform's tokens never pass by a client id, and its delegation tokens must
be bound to this Agent. The IdP beside it is never the platform, and its tokens whose `sub` starts with `sa:` or
`svc:` are refused (403 `forbidden`), since the platform issues no person token for such a `sub`. Either set alone
works as a single issuer; the same issuer in both fails the start with `duplicate_issuer`.

With `DAEGAM_CORS_ORIGINS` set, Starlette's `CORSMiddleware` is the outermost layer: it answers preflights (200) and adds
`Access-Control-Allow-Origin` and `Vary: Origin` to every response (SSE 200 and the 401, 403 and 429 errors included). It
allows the methods `GET`, `POST`, `PATCH`, `DELETE` and `OPTIONS` and the headers `authorization` and `content-type`,
exposes `Retry-After`, `X-Daegam-Session-Id`, `X-Daegam-Turn-Id`, `X-Daegam-Detached-Turn` and `Content-Disposition` (a
session file's download name), lets preflights
be cached for 600 s, and sends no credentials (`agent-runtime/runtime/main.py` `create_app`).

**Turn delegation tokens (capability `turn_tokens`, P53).** `/chat`, `POST /sessions/{sid}/decisions` and
`POST /sessions/{sid}/regenerate` take an optional `turn_grant` `{id, secret, sub, tokens: [{kind, id, token}],
expires_in, renew_url}` on the platform path; the external path answers a body that carries one with 422
`validation_error` (`runtime/grant_gate.py`). Its `sub` must be the session owner (the caller for a new session), or
on a resume the decider the platform marked as an approver; the owner's grant is refused when a decider other than the
owner sends their own input (an `edit`, a `respond`, or a `reject` with any message), and a mismatch is 409
`turn_grant_mismatch`. A response that took a grant carries its id in `X-Daegam-Turn-Grant`, and `turn_start` carries
`grant_id`. A source takes the token whose `kind` and `id` match its `tools[].source`; that turn's calls to it go
through a client of the turn's own, found in a context variable the turn sets before the graph runs and its tool tasks
and subagents inherit, while list refreshes and turns without a token for the source use the pod's credential. The
runtime renews at `<renew_url>/renew` when a third of `expires_in` remains, measured on its own monotonic clock, with
the instance token and the grant's secret; it retries 429, 5xx, connection errors and a malformed answer until the
tokens expire and stops on any other 4xx (401, 403, 404, 410). A call whose token has expired is not sent and answers
as a tool error, a call in flight when its token ends is cancelled at its next request and answers that it may
already have taken effect (the turn then drops that source's client), and a call outside any turn while a grant is
open fails as a tool error too. Before the turn releases its session's lease it posts `{secret, reason}` to
`<renew_url>/end` (`done`, `error`, `interrupt`, `cancelled`, or `shutdown` for a turn a shutdown stopped); a pod that
stops with turns open sends `shutdown`. A renewal refused with 403 (the person lost access) stops the turn as
`turn_access_lost`, and during a shutdown a 401 (the instance token was revoked) stops it as `turn_aborted`.
Tokens and the secret stay in memory only (`runtime/turn_grants.py`). When the first issuer is the platform
(`DAEGAM_OIDC_JWKS_URL` set, or `DAEGAM_IDP_ISSUER` beside it), the external path refuses a platform token that carries
`act` or `bound_to` unless `bound_to` is `agent:<agent id>` (403 `forbidden`); tokens of the IdP beside it are not
checked for this.

**Tool traffic safety (document feature `tool_safety`, P43, D96).** `/chat`, `POST /sessions/{sid}/decisions` and
`POST /sessions/{sid}/regenerate` take an optional `approval_choices` `[{tool, choice}]` (`approve` or `reject`) on the
platform path; the external path answers a body that carries one with 422 `validation_error`. The choices live in the
turn context only. A result from outside reaches the model inside `<outside_content source="<tool>">`, its `tool_result`
carries `untrusted: "outside"`, and the session index stores `outside_at` before the result returns; when that write
fails, the call answers `outside_mark_failed` instead of the content. Once a session holds outside content, every write
asks with the reason `outside`. A waiting approval lives in the checkpoint and the decision resumes from it, so the
runtime asks only when every decision reaches that checkpoint: with a memory node the replicas share it, and with the
document feature `in_pod_state` the Agent runs one pod that holds all of its state. The platform sends `in_pod_state`
only for an Agent preview whose source has a memory node (P44b section 7), and a decision resumes on the same pod; when
the pod restarts, the waiting approvals go with its conversations. Without either, such a write is refused as
`outside_writes_refused`, any other call that would need approval as `approval_unavailable`, and the prompt says that
writes are refused. A remembered reject
refuses as `tool_choice_rejected`. Every approval request carries `reason` (`rule` or `outside`) in the `interrupt`
event and in `GET /sessions/{sid}/pending`. Web tool results carry `untrusted: "web"` on every document (readers treat
an older `true` as `web`).

**Detached turns (capability `detached_turns`, P78, D92).** Every turn (chat, decision, regenerate) runs as a task of
its own (`runtime/turn_task.py`); the response only reads the turn's event queue, which is unbounded and sends
`: keepalive` every 15 s while quiet. A closed connection, even before the first byte, stops the reading, not the turn,
which settles and releases its lease as usual. Turns stop only on a stop request (`turn_cancelled`), a renewal refused
for lost access (`turn_access_lost`, counted as `cancelled` in `turn_end`) or a shutdown (`turn_aborted`, counted as an
error). The transcript is saved as items close: at the end of every graph chunk a writer task of the turn appends the
closed items from the start of its buffer (a streaming bubble or a call card without its result holds the rest), so the
turn itself never waits on the store while its deadline is armed; a failed append is retried after 5 s and the rest
goes with the final save; a regenerate that branches saves from the moment its head moved. On SIGTERM the server stamps the time and
waits `DAEGAM_TURN_DRAIN_SECONDS` (rendered by the platform; without it, no drain) for running turns, keeping open
readers until the drain plus 45 s; at the drain's end it stops the rest together as `turn_aborted`, and the lifespan
waits for their settlement before it closes tool sources, grants and the store. Without a memory node a turn that no
reader watches any more is stopped at once (`runtime/drain.py`).

### Observability events

One JSON line each on stdout. With `DAEGAM_EVENTS_URL` and the instance token the shipper (`runtime/shipper.py`) also
pushes each event to the platform's `POST /api/telemetry/events`; a pod that does not push is read from its log by the
platform's `AuditCollector`. Both paths land in `agent_events` under `<instance id>:<event id>`. Every line has
`daegam_event`, `id` (uuid4 hex, the event's idempotency key), `ts` (ISO 8601, milliseconds, UTC), `n` (the line number
this process wrote; the platform stores it as `seq` and orders events of the same millisecond by it),
`profile{id, name, revision}` and `instance{id, name}`. `?` marks fields present only sometimes; of those, the bodies
`message`, `args`, `content`, `text` and `structured_response` appear only with `service.observability.record_bodies`
true, pass every `pii_mask` rule of the agent whatever its position, and are cut at 8000 characters. A line over 64 KiB
loses its bodies and gets `truncated: true`. `user_sub` is always the session owner, except in `decision` and
`rejected`.

A run is one `/chat`, `/decisions` or `/regenerate` request and one trace (P37). Ids have the W3C Trace Context shape:
`trace_id` 32 and `span_id` 16 lowercase hex characters, drawn by the runtime. The run span is `turn_end`; `model_call`
and `tool_exec` are spans inside it, and a span is emitted once, when it ends, with `start` (ISO 8601) and `duration_ms`.
Spans carry `trace_id`, `span_id` and `parent_span_id` (the run span, or the `task` span for what a sub agent runs);
the point events inside a run (`interrupt`, `decision`, `guardrail`, `budget`, `model_fallback`, `model_retry`,
`tool_limit`) carry `turn_id`, `trace_id` and `parent_span_id` (the run span). A model call's id is
`<trace_id>-<span_id>`.

| `budget` | `user_sub`, `scope` (`session` or `daily`), `action` (`turn_ended` or `rejected`), `used`, `limit`, `session_id?`, `turn?`, `retry_after?` | A budget was passed. `turn_ended` means the session budget ended a turn, `rejected` an entrance 429 |
| `rate_limited` | `user_sub`, `limit`, `count`, `retry_after`, `window`, `session_id?` | The per-user minute limit was passed (429) |
| `rejected` | `user_sub` (the caller; null for the attachment checks, which do not know the caller), `code`, `session_id?` | An entrance rejection without its own event: 413 `max_input_chars` and `attachments_too_large`, 422 for the attachment checks (`too_many_attachments`, `attachments_need_filesystem`, `images_unsupported`, `invalid_attachment`) and for a blocked edited argument (`guardrail_blocked`, next to its `guardrail` event, whose position is `tool`), 429 `max_turns`, `max_concurrent_sessions` and `max_regenerations`, 503 `tools_unavailable`. With `rate_limited`, `budget{action: rejected}` and an `input` `guardrail` block it is what the platform counts as rejections |
| `model_fallback` | `session_id`, `user_sub`, `turn`, `from`, `to`, `agent?` | Retries are used up and the call moves to the fallback model |
| `model_retry` | `session_id`, `user_sub`, `turn`, `attempt`, `model`, `agent?` | A model call is retried after a transient error |
| `tool_limit` | `session_id`, `user_sub`, `turn`, `limit`, `agent?` | A run crossed its tool call limit (T82); the same event as the SSE one |
| `injection_check` | `session_id`, `user_sub`, `turn`, `tool`, `outcome` (`timeout`, `failed`, `refused`, `unlabelled`, `cap`), `category?`, `partial?`, `agent?` | The judge model did not label an outside result (a call over 10 s, a failed call, a refused answer with its `category`, an answer without a label, or a result past `max_calls`); the result passes as outside content |
| `web_guard` | `session_id`, `user_sub`, `turn`, `code`, `tool`, `host?`, `reason?`, `agent?` | The web guard refused a web tool call (`url_not_in_conversation`, `url_blocked`, `url_not_allowed` with its `reason`, `rate_limited`, `web_turn_limit`, `web_no_turn`); the URL is not carried (web-tools.md section 5) |
| `tools_refreshed` | `tools[]` | The graph was compiled again: the tool lists changed, or it became ready for the first time after start (even with an empty list) |
| `session_expired` | `session_id` | The sweep closed a session after its TTL (the first round runs at start); the transcript stays until the retention ends |
| `session_deleted` | `session_id`, `user_sub` | The owner deleted the session with `DELETE /sessions/{sid}` |
| `memory_deleted` | `user_sub` | The owner deleted one memory file with `DELETE /memories/files/{key}`. No path: through the platform proxy the platform audit keeps what was deleted as the path URL; through the external path only this event's subject remains |

## Feature names and init steps

The `agent.json` version ladder stops at `"3"`, and new runtime features are declared by name (D65). A name is one
lower-snake identifier (`^[a-z][a-z0-9_]{0,31}$`), and `runtime/features.py` keeps two lists. Document features
`DOCUMENT_FEATURES` appear in the optional `agent.json` key `features[]`; runtime capabilities `CAPABILITIES` (routes and
events) never appear in the document. `KNOWN` is their union. The platform's
`platform/daegam/services/agent_features.py` keeps the same two lists and a platform test compares the files, so a new
name goes into both.

| Capability | Routes and fields |
|---|---|
| `cancel` | `POST /sessions/{sid}/cancel` |
| `session_admin` | Session titles, `PATCH` and `DELETE /sessions/{sid}`, `q` of the session list |
| `regenerate` | `POST /sessions/{sid}/regenerate` |
| `citations` | `cite` in search results, the SSE `citations` event, `citations` on transcript tool cards |
| `memory_files` | `GET /memories`, `GET` and `DELETE /memories/files/{key}` |
| `attachments` | `attachments` in the `/chat` body, `done.attachments_received`, `attachments` on transcript user items |
| `session_files` | `GET /sessions/{sid}/files`, `GET /sessions/{sid}/files/{path}` |
| `redis_tls` | A Redis binding's `<PREFIX>_TLS`, `<PREFIX>_CA_FILE` and `rediss://` URLs (P61) |
| `telemetry` | The `model_call` and `tool_exec` spans, the `traceparent` correlation header and the event shipper (P37) |
| `detached_turns` | Turns that outlive their connection (P78): `X-Daegam-Turn-Id` and `X-Daegam-Detached-Turn`, `running` and `turn_id` on session rows, `view=progress`, `turn_id` of `POST /sessions/{sid}/cancel`, `POST /turns/cancel` |
| `runs` | Background run sessions (P41): `run_id` and `untrusted` of `/chat`, 409 `run_exists`, `X-Daegam-Run-Id`, `run_id` of decisions, `runs` of the session list and `run_id` on its rows, `run_id` on `turn_start` and `turn_end` |
| `agent_tasks` | Task sessions: `task` of `/chat`, a run session that stays open between turns, `session_id` with a new `run_id` as the next run of a task session, 409 `run_exists` for every run the session holds. On the calling side: `tools[]` entries with `mode: task` and the five task Tools (`runtime/agent_task_tools.py`) |
| `scale_to_zero` | Scale to zero (P44): `POST` and `DELETE /drain`, 503 `agent_draining` for lease claims under the drain mark in all three index kinds, the first sweep at start and the expired memory sweep at start, and sessions past their TTL read as closed |
| `two_issuers` | Two issuers for external tokens (P53b): the `DAEGAM_IDP_*` env beside `DAEGAM_OIDC_*`, picked by the token's `iss`, each with its own rules |

The document features are `provider_extra_body` (the provider's `extra_body` goes to `ChatOpenAI`; OpenRouter vendor
preferences use it), `skills` (section "Skills"), `provider_stream_usage` (a provider saved with `stream_usage:
false` does not ask for streamed usage; the runtime estimates its tokens from the text, P37), `web_guard` (the
top-level `web_data_tools` and the per-source `tools[].web` that the web guard reads, P39b), `tool_safety` (section
"API", the paragraph "Tool traffic safety", P43), `code_execution` (the top-level `code_execution`, P40),
`llm_gateway` (`gateway: true` on providers, P38), `in_pod_state` (no key of its own: the Agent's state lives in its
one pod, so `tool_safety` asks for approval without a memory node, P44b) and `injection_check` (the `injection_check`
rule of a `position: tool` guardrail, which needs `tool_safety`, P43) and `agent_tools` (`tools[]` entries with
`source.kind: agent`, which carry `description` and `timeout_seconds` and one Tool name in `allow`, and no `transport`,
`auth`, `web`, `inside` or `read`; `runtime/agent_calls.py` builds their Tools, and with `tool_safety` their results
always count as outside content and their calls as writes. An entry with `mode: task` carries the five task Tool
names in `allow` and no `timeout_seconds`; with `tool_safety` its `read` may name `check_async_task` and
`list_async_tasks` and its `inside` the four Tools other than `check_async_task`, whose result is the called Agent's
answer and always counts as outside content. The platform sends such entries only to images that report the
capability `agent_tasks`).

- **Init reports.** The Agent pod's init container runs this image and the fetch script the platform renders, with
  `python -c`. The script sends `runtime.features.KNOWN` in the header `X-Daegam-Runtime-Features`, env
  `DAEGAM_AGENT_IMAGE` in the header `X-Daegam-Runtime-Image` and, when the pod template has one, env
  `DAEGAM_MCP_TOKEN_TABLE` (the digest of the template's MCP Server token table) in the header
  `X-Daegam-Mcp-Token-Table`, so the compiled `agent.json` names the token envs this pod has
  (agents.md section 5). It fetches `agent.json` from the address the
  render gives (env `DAEGAM_AGENT_CONFIG_URL`). It follows no redirect, because the instance token is a platform secret; a 3xx stops
  it as `http_<status>`. The platform records the names as this Agent's record and uses them for deploy decisions and
  to gate proxy routes (agents.md section 2). An image
  without the module sends no header, and the platform reads that as an empty list.
- **Init steps.** After a successful fetch, for every name in the document's `features` that has a module
  `runtime.init_steps.<name>`, the script calls its `run(config_dir, fetch)`. `config_dir` is the config volume, and
  `fetch(path)` opens a path under this Agent's config root (env `DAEGAM_CONFIG_BASE_URL`) with the same token and
  headers and returns a read stream. What a feature does at init goes into this package, not into the script, so a new
  step does not change the rendered script and roll every agent. The only step today is `skills`.
- **Start-up check.** An unknown name in the document's `features` is caught before the schema check, and the runtime
  stays up but answers every request except `/healthz` with 503 `runtime_image_too_old`. The readiness probe
  `/healthz?probe=ready` is 503 too, so the new pod never turns Ready, the rollout stops and the old pods keep answering;
  the liveness probe `/healthz` is 200, so the pod does not restart in a loop. Documents of version `"1"` to `"3"` run as
  they are.
- **Checking.** `/healthz` (with the instance token) and `/metrics` carry `runtime{features}`. They are for checking;
  decisions use the record the platform wrote at the init fetch.

## Skills

A document with the feature `skills` (D64) carries the top-level `skills[{name, id, revision, digest, bytes}]` and the
per-agent name lists `main.skills` and `subagents[].skills`. The schema accepts these keys only when `features` has the
name, and the loader checks unique names (`duplicate_skill`) and that per-agent names exist (`unknown_skill_ref`).

- **Init step.** `runtime/init_steps/skills.py` checks the pins of `agent.json` again against the keys of
  `$defs/skill_pin` and the name rule `$defs/skill_name`, then fetches the Skills one by one from
  `GET /api/agents/{id}/skills/{name}`, checks the `$defs/skill_bundle` shape and the path rule `$defs/skill_path`, and
  recomputes the digest to compare with `agent.json`. It writes each attached agent's copy to
  `<config volume>/skills/main/<name>/…` and `skills/sub-<i>/<name>/…` (i is the position in `subagents[]`) and locks
  files 0444 and directories 0555. Everything is written to a temporary directory first and renamed; when called again,
  what an earlier attempt left is unlocked and removed and the step starts over. Connection failures, bodies cut while
  reading and 5xx are retried three times after 1, 2 and 4 s. On failure it writes `<code>: <text>` to
  `/dev/termination-log`: a failed fetch is the platform error's `detail.code` (`http_<status>` without one) or
  `unreachable`; a pin that does not match the response is `skill_bundle_invalid`, `skill_path_invalid` or
  `skill_digest_mismatch`; a failed write to the config volume is `skills_write_failed`. It imports only the standard
  library.
- **Runtime.** `runtime/skills.py` mounts the config volume's `skills/` as the `/skills/` route. The main agent reads
  `/skills/main/` and sub agent i `/skills/sub-<i>/`, and a `SkillsMiddleware` with our wording instead of the default
  prompt (which talks about running scripts) replaces the default one in place under the same name. The ephemeral turn
  graph has the same route. When the main agent has Skills, every turn's input carries `skills_metadata: None`, so a
  session that continues after a redeploy reads the new list; sub agents read theirs on every `task`.
- **Read-only.** The config mount is read-only, and before that the `/skills/**` `write` rule (write, edit, delete)
  refuses at the tool level for the main agent and sub agents. The rule is added only for documents that have the
  `/skills/` route.
- **Start-up check.** With the main agent's `builtin_tools.filesystem` false the start fails with
  `skills_filesystem_disabled`; an attached SKILL.md not in its place fails it with `skills_missing`.

## Development

```
cd agent-runtime
uv sync
uv run ruff check . && uv run ruff format --check .
uv run pytest -q
docker build -t daegam-agent-runtime:dev .
```

Tests that need Postgres or Redis skip unless `DAEGAM_TEST_PG_DSN` and `DAEGAM_TEST_REDIS_URL` are set.
`scripts/local-test-dbs.sh up` starts local test stores (Homebrew MongoDB, Postgres and Redis Stack) and
`eval "$(scripts/local-test-dbs.sh env)"` sets both addresses, after which `make verify-runtime` runs those tests too;
`make runtime-db-up` starts the same stores as containers instead. `python3 schema/check.py` checks the fixtures and
the contract violation examples against `schema/agent.schema.json`.

To run it locally:

```
DAEGAM_AGENT_CONFIG=schema/fixtures/support-agent.json uv run python -m runtime.main
```

The fixture's MCP URLs are in-cluster addresses, so loading tools fails; use a copy with `memory` set to `null` and
`tools[].url` pointed at a server you can reach.
